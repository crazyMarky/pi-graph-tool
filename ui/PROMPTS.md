# 复杂任务提示词集（用于测试图调度效果）

> 用途：让主 agent 调用 `graph_run` 时生成**多 Wave、多跳依赖、带工具节点**的深图，检验拓扑分层、数据路由、屏障与失败语义。
> 写法要点：**显式声明阶段**（"第 N 阶段……"），并注明"阶段间严格依赖、同阶段内互不依赖"——这两句是让模型生成深 DAG 而非单层并行的关键。
> 注：实际生成的节点数/波数取决于模型的拆解判断（这本身就是编排智能的观测点）；GLM-4.5 实测 P1 生成 8 节点 / 4 Wave。

## P1 深流水线：四阶段技术选型（实测 8 节点 / 4 Wave）

```
请分阶段完成一项技术选型分析：第一阶段，并行调研 PostgreSQL、MongoDB、Redis 三种数据库的核心原理与典型适用场景；第二阶段，基于第一阶段结论，分别评估三者用于电商订单系统的优势与短板；第三阶段，交叉核对第二阶段评估的关键假设，指出矛盾或存疑之处；第四阶段，汇总为不超过400字的选型建议。阶段间严格依赖，同阶段内子任务互不依赖。
```

**看点**：4 个 Wave 逐级推进；第二阶段的每个评估节点用 `{{调研id}}` 消费第一阶段产出（两跳数据路由）；屏障放行动画。

## P2 翻译-审校-终审流水线（三波纯文本加工）

```
现有三个前端框架 React、Vue、Svelte 的定位需要三阶段处理：第一阶段，为每个框架并行撰写一段80字中文定位摘要；第二阶段，把三段摘要各自翻译成英文（依赖第一阶段对应摘要）；第三阶段，对三段英文做术语一致性交叉审校，输出一份统一术语表的终稿（依赖第二阶段全部）。阶段间严格依赖，同阶段内互不依赖。
```

**看点**：菱形依赖（三个独立分支 + 汇聚审校）；第二阶段的"依赖第一阶段**对应**摘要"会生成一一对应的边而非全连接（观测 LLM 的依赖精度）。

## P3 带工具节点：文件调研流水线

```
请帮我分析本项目目录下的文档：第一阶段，并行读取并归纳根目录下每一类文件的内容主题（需要读文件的节点可以用 read 工具，各自在独立子目录工作）；第二阶段，交叉对比各主题，找出重复覆盖与空白；第三阶段，输出一张主题地图。阶段间严格依赖，同阶段内互不依赖。
```

**看点**：带 `tools:["read"]` 的工具节点（卡片上有 ⚙ 标记）；workdir 隔离；对照纯 LLM 节点的耗时差异。

## P4 决策树评估：方案对比四波

```
针对"自建机房 vs 公有云 vs 混合架构"三个方案做决策分析：第一阶段，并行分析三个方案各自的可行性；第二阶段，为每个方案并行列出风险清单（依赖第一阶段对应方案的分析）；第三阶段，综合三个方案的风险做交叉评分（依赖第二阶段全部）；第四阶段，输出推荐结论与理由。阶段间严格依赖，同阶段内互不依赖。
```

**看点**：3×3 的阶段矩阵 + 汇聚评分；观察模型是否正确建立"对应方案"的窄依赖而非全连接依赖。

## P5 多跳调研：候选→深挖→冲突检测

```
请完成一项开源组件选型：第一阶段，并行确定 2025 年最活跃的三个 Agent 编排框架（每个候选一个节点，列出名称与活跃度依据）；第二阶段，对每个候选调研其依赖结构与许可证（依赖第一阶段对应候选）；第三阶段，检测三个候选之间的许可兼容性冲突（依赖第二阶段全部）；第四阶段，输出合规选型建议。阶段间严格依赖，同阶段内互不依赖。
```

**看点**：真正的"两跳路由"——候选名称要经第一、二阶段两次传递才到达第四阶段；适合验证 `{{id}}` 数据路由的保真度。

## P6 失败语义观测（可选，故意触发违约）

```
请组织一个流水线：第一阶段，三个节点各自只输出一个数字（7、3、9），不要输出任何其他文字；第二阶段，把三个数字相加，只输出结果数字。阶段间严格依赖。
```

**看点**：超短输出触发契约违约 → 挽回重试（琥珀色脉冲 + "重试挽回"徽标）→ 接受非空结果；若两次皆空则失败并级联跳过第二阶段（灰化 + 原因）。适合演示失败语义（注意：GLM 系模型可能把超短回答放进思考通道导致失败——这本身是厂商行为差异的活教材）。
